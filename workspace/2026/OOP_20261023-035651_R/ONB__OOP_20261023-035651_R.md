## 5. Risks Found (edge cases, potential issues not in TS)

1. `normalizeLab()` can also filter unsupported answer/checklist members from an otherwise object-shaped record. The approved correction must preserve the original value when the record is not safely interpretable; it must not silently classify partially retained data as fully understood.
2. A wholly invalid top-level progress document already makes the entire store unwritable. The approved behavior concerns preserving/refusing an affected lab record while allowing unrelated valid records to save; do not broaden the failure contract without an owner decision.
3. A browser storage restriction or unavailable Chrome would leave AC-2 unproved. Record `DEFERRED` and keep acceptance open rather than treating the Node regression as a substitute.

## 6. Inconsistencies with Code (spec vs reality)

- TS §2 requires preservation of unsupported per-lab data and refusal to update that same lab until explicit reset. Current `readProgress()` omits a failed `normalizeLab()` result, then returns a writable snapshot; a later `persist()` serializes only the normalized map. `saveLabWork()` supplies a new `started` record when the selected lab is absent from that map. These paths can overwrite or remove the original value.
- TS §2 requires a clear warning for the affected lab. Current `app.js` warns when the entire progress object is unwritable, but its per-lab start/save calls otherwise use a success boolean and do not identify an unsupported raw entry.
- TS §5 requires ordinary valid-lab saving and explicit reset to retain existing behavior. Current reset removes only `oopoman.progress.v1`, matching the contract in `course/README.md` and `NorthStar.md`; preserve that boundary.
