## 1. Objective

Deliver six connected, locally previewable week-3 course pages for lectures and labs 7–9. Each page uses Python, accessible Russian explanations, a meaningful UML diagram, and a complete self-contained code example with its expected output. The required lesson route fits the existing 60-minute core; optional depth is clearly separated. The owner can inspect the in-progress module on the local site. The unfinished course is not published.

The payment case in Lab 7 keeps the original transit-gateway meaning through a fictional local request/result contract. It does not connect to any provider or network and makes no payment. Stripe and Adyen documents appear only as a short real-world comparison of object boundaries and differing lifecycles, not as the fictional API specification.

## 2. Scope

### In Scope

- Add lecture and lab pages 7, 8, and 9 to the existing course data and page-shell structure; use Python on all six pages.
- Give each lesson an understandable explanation of the relevant OOP ideas, first-use definitions for technical terms, a useful UML view, and a complete standalone Python program plus expected output. Do not rely on earlier code blocks or hidden setup.
- Keep each lab aligned with its lecture. Include the existing course practice format, a student checklist, and five questions per lab.
- Lab 7 retains a transit payment gateway and shows a fictional local adapter/request/result boundary. The required core uses one simple result (approved/declined) and a clear stop/error example. It does not teach retry, idempotency, or a real provider lifecycle as universal behavior. Optional depth may discuss why real provider contracts differ, with official Stripe/Adyen references and explicit limits.
- Lab 8 covers the approved Chain/Observer learning outcomes; Lab 9 uses a small local Clean Architecture example and its dependency rule. Align each with its source PDF without carrying forward the source course’s unrelated future-week promises.
- Enable Module 3 for the owner’s local development preview while keeping unfinished work out of public distribution. Add the UML assets to the local build output so the preview renders them.
- Update `course/README.md`, `NorthStar.md`, and `CHANGELOG.md` to describe the implementation and preserve the local-preview/acceptance boundary.
- Provide per-criterion evidence, an independent review, explicit owner acceptance, and a final task-bound Economics report from actual accepted results and available resource captures.

### Out of Scope

- Editing existing lessons/labs 1–6 or changing their language; changing any source PDF.
- Live API use, network requests, provider accounts, credentials, payment data, actual/test transactions, or a production payment integration.
- Selecting a commercial provider, asserting local merchant/acquirer/KZT eligibility, or giving compliance/production payment advice.
- Server execution of Python, automatic grading, authentication, a backend, an exam, or public deployment/publishing.
- Claiming measured student learning or a proven 60-minute fit without student evidence.
