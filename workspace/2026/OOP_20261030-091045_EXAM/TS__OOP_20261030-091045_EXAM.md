## 1. Objective

Deliver a static OOPoman exam that lets a student complete a timed, source-aligned assessment and receive a clear local score, pass status, criterion feedback and course rating. A pass at 30/40 records successful completion of the course. This task creates no certificate and sends no result outside the browser.

## 2. Scope

### In Scope

- Add an exam page linked from the course home, with the approved name choices, rules, timer, 20 single-answer questions and three practical coding tasks.
- Use only the original lecture and lab PDFs as evidence for exam topics and criteria. Keep a separate teacher key with answer rationales, source pages, practical solutions and complete rubrics outside `course/` and the generated `dist/`.
- Grade 20 questions at 1 point each (Modules 1/2/3: 8/7/5) and practicals at 4/6/10 points (лёгкая/средняя/продвинутая), for 40 total and a pass at 30.
- Run practical answers only through the existing course terminal after its approved interface/readiness covers all three modules and the owner has agreed the shared-file route with OOP_20261029-184453_RT.
- Store the current attempt, result and any rating only under `oopoman.exam.v1`; preserve `oopoman.progress.v1` and all existing course scoring/completion behavior.
- Keep the exam unavailable to the intended audience until all three modules are available there and the terminal dependency and file route are ready.

### Out of Scope

- A certificate, credential, certificate page/download, backend, account, authentication, server-side answer secrecy, external result/rating submission, anti-cheating enforcement or a parallel code runner.
- Changes to the course's existing progress key, quiz scores, lab checklist, peer-check, completion rules, source PDFs, course lesson/lab content or RT task scope.
- Using website text, `course/data.js`, HTML or `dist/` as educational evidence for exam content. These may be read only to integrate with the site.
- Public exam availability while Module 3 is locked or the approved terminal integration is unavailable.

## 6. Technical Guidance

- Keep the exam as a dedicated static page and keep its behavior in an exam-specific script; integrate it with the existing course home and visual system.
- Keep all exam state isolated under `oopoman.exam.v1`. Do not use or refactor the existing course storage module unless the exact approved selector and owner approval change.
- Use the existing terminal's returned public interface. Do not copy its runtime, worker, assets or checks into an exam-specific runner.
- Browser-side correct answers and checks are inspectable by design. The teacher key is an instructor reference, not a secret-grade claim.
- Keep the interface accessible by keyboard and readable on narrow screens; show timer/deadline and submission status in text, not color alone.
- Source-content mapping is supplied by RES iteration 1. The Executor authors final stems and distractors within that map; this TS does not claim the research proved exam duration.

## 7. Definition of Failure

- ❌ The site exposes an attempt before Module 3 and the approved terminal are available to the intended audience.
- ❌ A parallel runner or unapproved terminal interface is introduced, or shared RT files are edited before the owner-agreed route.
- ❌ A question is not source-backed by an original PDF, has more than one defensible answer, or gives a visible answer-position cue.
- ❌ Any point lacks an atomic criterion and expected outcome; failed mandatory criteria display a task as complete; or timeout ignores current answers.
- ❌ Exam state affects `oopoman.progress.v1`, points, lab completion or sends data externally.
- ❌ Teacher key enters `course/`, browser-loaded resources or `dist/`, or product copy claims identity/authenticity/anti-cheating protection.
- ❌ A certificate is generated, offered or awarded.
- ❌ Candidate accounting cannot be reproduced against the exact selector/baseline or exceeds the approved denominator without a prior owner decision.
