## 1. Objective

Deliver a standalone OOPoman exam page, separate from module pages, that lets a student complete a timed, source-aligned assessment and receive a clear local score, pass status, criterion feedback and course rating. A pass at 30/40 records successful completion of the course. This task creates no certificate and the exam app sends no attempt or result data to a service.

## 2. Scope

### In Scope

- Add a standalone exam page linked from the course home, with the approved name choices, rules, timer, 20 single-answer questions and three practical coding tasks. It is independent of module-page availability and course module progress.
- Use only the original lecture and lab PDFs as evidence for exam topics and criteria. Keep a separate teacher key with answer rationales, source pages, practical solutions and complete rubrics outside `course/` and the generated `dist/`.
- Grade 20 questions at 1 point each (Modules 1/2/3: 8/7/5) and practicals at 4/6/10 points (лёгкая/средняя/продвинутая), for 40 total and a pass at 30.
- Execute practical Python answers inside an exam-owned Pyodide runtime in a dedicated module web worker. Load the version-pinned runtime before the attempt starts; require HTTP(S) hosting and show a clear unavailable state when the runtime cannot load.
- Store the current attempt, result and any rating only under `oopoman.exam.v1`; preserve `oopoman.progress.v1` and all existing course scoring/completion behavior.
- Keep question answers and practical grading checks client-side and inspectable. Do not pass the student's selected name, exam record, rating or course storage to the runtime worker.

### Out of Scope

- A certificate, credential, certificate page/download, backend, account, authentication, server-side answer secrecy, external result/rating submission, anti-cheating enforcement or integration with any module runtime.
- Changes to the course's existing progress key, quiz scores, lab checklist, peer-check, completion rules, source PDFs or course lesson/lab content.
- Using website text, `course/data.js`, HTML or `dist/` as educational evidence for exam content. These may be read only to integrate with the site.
- Guaranteeing that a browser worker is a secure sandbox or can prevent student-authored code from attempting network access.

## 6. Technical Guidance

- Keep the exam as a dedicated static page and keep its behavior in an exam-specific script; integrate it with the existing course home and visual system.
- Keep all exam state isolated under `oopoman.exam.v1`. Do not use or refactor the existing course storage module unless the exact approved selector and owner approval change.
- Pin Pyodide to `https://cdn.jsdelivr.net/pyodide/v314.0.7/full/pyodide.mjs` and run it in a module worker; do not use the unversioned `stable` URL at runtime.
- Initialize the worker before “Начать экзамен”, so CDN loading time is outside the 60-minute attempt. A worker has no direct DOM access; do not pass it student identity, saved attempt data, rating or course storage.
- Bound each evaluation to 10 seconds. If it exceeds the bound, terminate and replace the worker, mark unverified practical criteria failed with a timeout explanation, and keep the page responsive.
- Do not claim that arbitrary student code cannot make network requests or that worker termination creates a hardened security sandbox. The exam app itself must not transmit attempt or result data.
- Browser-side correct answers and checks are inspectable by design. The teacher key is an instructor reference, not a secret-grade claim.
- Keep the interface accessible by keyboard and readable on narrow screens; show timer/deadline and submission status in text, not color alone.
- Source-content mapping is supplied by RES iteration 1. The Executor authors final stems and distractors within that map; this TS does not claim the research proved exam duration.

## 7. Definition of Failure

- ❌ The exam requires module-page availability/progress, or its own runtime executes on the page's UI thread.
- ❌ The page starts the timer before runtime readiness, silently treats a loading/runtime error as a passing result, or allows evaluation to run indefinitely.
- ❌ A question is not source-backed by an original PDF, has more than one defensible answer, or gives a visible answer-position cue.
- ❌ Any point lacks an atomic criterion and expected outcome; failed mandatory criteria display a task as complete; or timeout ignores current answers.
- ❌ Exam state affects `oopoman.progress.v1`, points, lab completion or sends data externally.
- ❌ Teacher key enters `course/`, browser-loaded resources or `dist/`, or product copy claims identity/authenticity/anti-cheating protection.
- ❌ A certificate is generated, offered or awarded.
- ❌ Candidate accounting cannot be reproduced against the exact selector/baseline or exceeds the approved denominator without a prior owner decision.

## 8. Phase Risks

| Risk | Mitigation |
|---|---|
| Practical work plus questions cannot fit 60 minutes | Keep each task to the named source-backed subset; measure a timed run before release; do not publish while the fit is unproven. |
| Pyodide CDN or browser support is unavailable | Require HTTP(S), show runtime readiness and failure clearly, and do not start the attempt until the runtime is ready. |
| Student code loops or exceeds execution time | Run in a worker with a 10-second evaluation limit and terminate it on timeout; disclose that this is not a hardened sandbox. |
| Front-end grading can be inspected or edited | Disclose the limitation; make no credential/security claim. |
| Local data is cleared or overwritten by another browser profile | State that results are profile-local and keep exam data separate from course progress. |
